# 개선 전/후 비교 평가보고서

> 작성일: 2026-10-01 · 근거 원장: [BUILD_SPEC.md](../BUILD_SPEC.md) 결정 로그, [REPORT.md](../REPORT.md) 6·7절

Builder·도구·프롬프트에 가한 개선 실험을 하나의 형식으로 모은 기록이다.
모든 사례는 다음 다섯 항목으로 적는다:

**가설 → 측정 방법 → 전후 건수 → 판정 → 회귀 확인**

판정은 세 가지뿐이다 — **개선**(전후 차이가 측정으로 검출됨), **미검출**(차이를
주장할 표본이 안 됨 — 개선이라 부르지 않음), **부작용**(다른 경로가 나빠짐).
원칙 두 가지가 전체를 관통한다:

- **기저율이 판정을 가른다.** 드문 현상의 개선은 소표본으로 주장할 수 없고(사례 8),
  흔한 현상의 개선은 소표본으로도 보인다(사례 9).
- **통과할 때까지 돌린 결과는 기준값이 아니다.** 원인이 수정과 무관하면 실패를
  그대로 기준값으로 남기고, 원인을 고친 뒤의 실행만 새 기준값이 된다.

## 요약

표본 열은 **근거 강도**를 드러낸다 — 판정은 당시 기준 그대로 두되, 서두 원칙과
같은 잣대로 읽을 수 있게 한다. 초기 사례(1·4·6)는 전후 각 1회 실행으로 판정했다 —
당시에는 반복 측정 관행이 없었고, 6.11(1회 표본은 운을 보고한다) 이후 기준이 생겼다.

## 사례별 상세

### 1. 도구·팀 판단 프롬프트 수정 (2026-08-10)

- **가설**: 1차 케이스 확장에서 드러난 실패(도구 과잉/과소 선택, 팀 과잉)는 프롬프트에
  판단 기준이 없어서다 — 기준을 명문화하면 통과율이 오른다.
- **측정 방법**: 평가 스위트(당시 9건, 기계적 검사 + 심판) 전후 실행.
- **전후 건수**: **5/9 → 8/9**.
- **표본**: 전후 각 1회 — **단일 실행, 근거 약함** (당시 반복 측정 관행 없음).
- **판정**: 개선.
- **회귀 확인**: 잔여 1건은 사례 2에서 별도 원인으로 판명 (프롬프트가 시스템에 없는
  상호작용을 약속).

### 2. Builder 질문 단계 제거 (2026-08-10)

- **가설**: 간헐 생성 실패는 프롬프트의 "모호하면 질문한다" 단계 때문이다 — 질문을
  받아줄 코드 경로가 없어(단발 호출) 되묻는 순간 재시도가 소진된다.
- **측정 방법**: 재시도 각 시도의 입출력 캡처로 원인 확정(1차 시도에 JSON 없음 —
  되물음) 후, 질문 단계를 "합리적으로 가정하고 description에 적는다"로 교체하고
  평가 재실행.
- **전후 건수**: **8/9 → 9/9, 2회 연속**.
- **판정**: 개선.
- **회귀 확인**: 이후 확장(12·21·27건)에서 질문-소진형 실패 재발 없음.

### 3. 「할 수 없는 일을 쓰지 않는다」 규칙 (2026-08-10)

- **가설**: 도구에 없는 능력(DB·이메일·셸)을 명세가 약속하는 실패는 금지 규칙이
  없어서다.
- **측정 방법**: 2차 확장 스위트(12건) 전후 실행.
- **전후 건수**: **10/12 → 12/12 (평균 4.92, 2회 연속)**.
- **판정**: 개선.
- **회귀 확인**: 정직성 계열 케이스가 이후 27건 체계까지 유지 통과 — 단,
  "사용자 환경 실행" 변형은 사례 9에서 다시 뚫린 것이 발견됐다.

### 4. 계산 전용 도구 `calculate` 분리 (2026-08-10, Phase 5-1)

- **가설**: 계산 요구에 `python_repl`(임의 코드 실행)이 선택되는 것은 대안 도구가
  없어서다 — 안전한 계산 도구를 주면 대부분의 생성 에이전트가 임의 실행 권한을
  받지 않게 된다.
- **측정 방법**: 평가 스위트에서 python_repl이 선택된 케이스 수 전후 비교.
- **전후 건수**: **7건 → 0건**.
- **표본**: 전후 각 1회 — **단일 실행, 근거 약함**.
- **판정**: 개선 (노출면 축소 — 위험 제거가 아니라 감소임을 문서에 명시).
- **회귀 확인**: 통과율 유지, `calculate` 자체는 집계가 가능해야 효과가 유지된다는
  조건이 붙었고(range·컴프리헨션 허용) 그 조건은 사례 7로 이어졌다.

### 5. 팀 판단 자기모순 1차 제거 (2026-08-10, REPORT 6.10)

- **가설**: `four_tools_one_request`가 같은 모델로 통과/실패를 오가는 것은 모델이
  아니라 프롬프트의 두 규칙("동사가 둘 이상이면 도구도 둘 이상" vs "단계마다 도구가
  다르면 팀")이 같은 입력을 반대로 보내기 때문이다.
- **측정 방법**: "단계마다 도구가 다르다"를 팀 근거에서 제거 후, 팀 판단이 걸린
  7케이스 재실행 + 뒤집히던 케이스 반복 실행.
- **전후 건수**: 간헐 실패 → **재실행 9/9, 뒤집히던 케이스 3회 반복 모두 단일**.
- **판정**: 개선.
- **회귀 확인**: 전체 스위트 통과 유지. 같은 계열 모순이 두 곳 더 남아 있던 것이
  사례 8에서 발견됐다.

### 6. 심판에게 팀원 도구·프롬프트 제공 (2026-08-10, REPORT 6.9-C)

- **가설**: 심판 감점("각 subagent의 도구가 명세에 명시되지 않아")은 명세 결함이
  아니라 심판이 팀원 이름만 받아 **보이지 않는 것을 채점**했기 때문이다.
- **측정 방법**: 심판 입력에 팀원 도구·description·프롬프트를 펼쳐 넣고 같은 케이스
  재채점.
- **전후 건수**: 해당 케이스 **4/5 → 5/5** (심판이 도구를 직접 인용).
- **표본**: 재채점 1회 — **단일 실행, 근거 약함** (다만 감점 사유 문구가 입력 결손을
  직접 가리켜 인과는 분명했다).
- **판정**: 개선 — 생성물이 아니라 **채점의 정확화**다. 채점 기준이 묻는 것은 심판이
  볼 수 있어야 한다.
- **회귀 확인**: 이후 전체 실행에서 "안 보이는 근거 감점" 재발 없음.

### 7. calculate 거부 메시지에 대안 힌트 (2026-10-01, REPORT 6.12)

- **가설**: 팀원이 미허용 함수(`all` 등)를 반복 시도해 한 턴이 28단계까지 늘어난 것은
  도구가 거부 사유만 주고 **대안을 주지 않아서**다 — 오류 메시지는 다음 행동의
  입력이다.
- **측정 방법**: 세 층위 수정(도구 설명에 허용/불가·대안, 오류 메시지에 허용 목록 +
  이름별 힌트, 템플릿 프롬프트에 재시도 금지 규칙) 후 같은 질문(1~50 소수 합) 2회
  실대화 — UI와 같은 단계 집계.
- **전후 건수**: **28단계 → 14단계(55.7s)·9단계(46.1s)**, calculate 오류 반복 → **0회**,
  정답(328) 유지.
- **표본**: 전 1회 · 후 2회 — 전측이 단일 관측이지만, 후측 2회 모두 미허용 식 시도
  자체가 사라졌다(28단계의 직접 원인 소멸).
- **판정**: 개선.
- **회귀 확인**: 레지스트리 변경이므로 공통 27건 재실행 — **27/27 (평균 5.00)**,
  직전 기준값(4.93) 대비 회귀 없음.

### 8. 팀 판단 자기모순 2차 제거 (2026-10-01, REPORT 6.14)

- **가설**: "조사해서 정리" 경계 문구의 간헐 팀 생성(발견 당시 3회 중 2회)은 사례 5가
  남긴 모순 — 판단 기준 목록의 "도구가 다른가"와 팀 예시의 "도구가 다르고" — 가
  원인이다.
- **측정 방법**: 경계 프로브 4종(발견 원문 + 프롬프트에 없는 새 문구 3종,
  `eval/boundary.py`)을 수정 전/후 각 5회 대칭 측정. 측정 문구를 프롬프트 예시로
  넣었던 중간 수정은 **과적합·프로브 오염**으로 기각.
- **전후 건수**: 발견 원문 **합산 2/8 → 1/5** (신규 3종은 전 구간 0/5). 오전 발견과
  오후 측정의 조건 차이(문구·호출 경로·레지스트리) 없음 확인 — 다른 것은 시점뿐.
- **판정**: **미검출** — 발생률이 낮아 이 표본으로 효과를 주장할 수 없다. 수정(모순
  제거)은 측정이 아니라 일관성 근거로만 유지한다.
- **회귀 확인**: common 27/27(4.96) · infra 7/7(5.00) · dev 6/8 — dev 실패 2건은
  전/후 프로브로 **이번 수정과 무관**(사례 9의 기존 약점)으로 판별, 실패를 그대로
  기준값으로 남겼다. 팀 기대 케이스 5종은 전부 팀 유지(과잉 억제 없음).

### 9. python_repl 실행 범위 명시 (2026-10-01, REPORT 6.15)

- **가설**: "사용자 환경(서버·프로젝트)에서 실행해줘"에 python_repl을 붙이고 실행을
  약속하는 것은, 프롬프트가 셸·DB 우회만 금지하고 **"사용자 기존 환경에서의 코드
  실행"** 범주를 빠뜨렸기 때문이다 ('파이썬'이라는 표면 일치가 유혹).
- **측정 방법**: '할 수 없는 일' 섹션에 범주 추가 + python_repl 실행 범위("이 시스템
  안의 빈 임시 프로세스, 맞는 경우는 제공된 코드·데이터 실행") 명시 — **측정 프로브
  문구는 예시로 넣지 않음**. 정직성 2케이스 + 셸 거절 케이스 + 정당-필요 프로브
  (세트 외, 부여가 정답)를 각 5회 실행.
- **전후 건수**:

| 대상 | 전 (repl 부여) | 후 (repl 부여 · 통과) |
|---|---|---|
| python_script_fix_honesty | **8/8** | **0/5 · 5/5** |
| dotnet_test_run_honesty | 3/8 | **0/5 · 5/5** |
| 셸 거절 케이스 (유지 확인) | 0 | 0/5 · 5/5 |
| 정당-필요 프로브 (부여가 정답) | — | **부여 5/5** |

- **판정**: **개선** — 기저율이 높아(8/8) 소표본으로도 검출된다. 정당-필요 프로브가
  "줄였다"와 "다 막았다"를 구분해 준다 (과잉 억제 없음).
- **회귀 확인**: common 27/27(4.96) · infra 7/7(5.00) · **dev 8/8**(4.88) — dev 8/8은
  통과할 때까지 돌린 것이 아니라 원인 수정 후의 실행이라 기준값 자격이 있다.

## 사례 8과 9가 나란히 보여주는 것

같은 날, 같은 방법(전/후 건수 비교)으로 한 두 실험의 판정이 갈렸다. 가른 것은 방법이
아니라 **기저율**이다 — 25%쯤 되는 드문 현상(사례 8)은 5회 표본으로 아무것도 말할 수
없고, 100%로 재현되는 현상(사례 9)은 5회로도 충분하다. 그래서 이 보고서는 "수정했다"와
"개선했다"를 구분해 적는다 — 측정으로 입증하지 못한 개선은 개선이라 부르지 않는다.
